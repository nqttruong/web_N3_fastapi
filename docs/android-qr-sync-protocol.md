# Android QR sync protocol v1 — Web implementation

**Status (2026-11-18):** Web API and mock client tested, including shared source-address rate limiting, replay checks and the claim/confirm/pull/revoke lifecycle. Current N3 Sensei Android has no QR scanner or claim client. **Web QR pairing ready; Android implementation pending.** Manual PR6 pairing remains compatible. QR pairing has not been checked against a real device or a deployed trusted HTTPS endpoint.

## Deployment and trust boundary

- Set `SYNC_PUBLIC_HTTPS_BASE_URL` to the externally reachable HTTPS **origin** (for example `https://jlpt.example.test`), without `/api/v1`. A phone must trust its certificate under normal Android platform validation. Loopback and `localhost` are rejected for QR creation. Do not disable certificate validation or expose the development server to the Internet.
- `/api/v1/sync/admin/*` requires the Web sync administrator credential when accessed remotely; the Settings UI keeps it only in memory. All sync routes require HTTPS outside loopback. Device endpoints require the credential stated below. A QR challenge is a short-lived pairing capability, not a device credential.
- Only one human-operated profile exists. No email/password account is introduced. A device is not paired until Web confirmation. Scanning alone grants no access to sync data.

## Sequence

```mermaid
sequenceDiagram
    participant W as Web Settings (admin)
    participant S as FastAPI + PostgreSQL
    participant A as Future Android client
    W->>S: POST /sync/admin/qr-sessions
    S-->>W: QR payload (5 minute session)
    W-->>A: QR shown to human; Android scans
    A->>A: Check v1, HTTPS origin, expiry; generate random device credential
    A->>S: POST /sync/qr-sessions/{id}/claim
    S-->>A: claim_ticket + 6 digit confirmation_code
    A->>S: POST /sync/qr-sessions/{id}/ready (X-Claim-Ticket)
    A-->>W: Show device name and confirmation code on Android screen
    W->>S: POST /sync/admin/qr-sessions/{id}/confirm (code)
    S-->>W: PAIRED + device_id
    A->>S: GET /sync/qr-sessions/{id} (X-Claim-Ticket)
    S-->>A: PAIRED
    A->>S: GET /sync/changes?cursor=0 (Bearer device credential)
    S-->>A: Ordered change page
    A->>S: POST /sync/push (Bearer device credential; review events)
```

All endpoint paths above are relative to `{base_url}/api/v1`. The QR contains no admin key, long-lived token, learning data, refresh token, or ChatGPT credential.

## Versioned QR payload

JSON encoded in QR; timestamps are ISO 8601 with timezone/UTC. `session_id` is UUID. `challenge` is a random URL-safe secret generated by the server; `expires_at` is five minutes after creation.

```json
{
  "version": 1,
  "base_url": "https://jlpt.example.test",
  "session_id": "00000000-0000-4000-8000-000000000001",
  "challenge": "<server-generated-URL-safe-random-value>",
  "expires_at": "2026-11-17T12:05:00Z"
}
```

Android must reject unknown version, invalid UUID, non-HTTPS/loopback base URL, expired timestamp, or unexpected keys before contacting the server. Do not log the challenge or device credential. The payload is never itself accepted as a bearer token.

QR payload JSON Schema (the server additionally rejects base URLs containing credentials, a path, query, or fragment):

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "additionalProperties": false,
  "required": ["version", "base_url", "session_id", "challenge", "expires_at"],
  "properties": {
    "version": { "const": 1 },
    "base_url": { "type": "string", "format": "uri", "pattern": "^https://" },
    "session_id": { "type": "string", "format": "uuid" },
    "challenge": { "type": "string", "minLength": 24, "maxLength": 100, "pattern": "^[A-Za-z0-9_-]+$" },
    "expires_at": { "type": "string", "format": "date-time" }
  }
}
```

## Pairing endpoints

Every success response wraps the documented object in `{ "data": ... }`. Validation errors follow FastAPI's error response. `401` indicates bad secret/code/ticket, `404` unknown session, `409` invalid state or replay, `422` malformed input, `429` source-address lockout (includes `Retry-After` seconds), and `503` missing/invalid trusted public HTTPS URL. Expired sessions transition to `EXPIRED` when next accessed. Five wrong confirmation codes transition that session to `FAILED`. Five invalid pairing attempts from one source address within 15 minutes lock the source for 15 minutes using the existing PR6 `sync_pairing_attempts` table; only a SHA-256 address hash is stored. A bad QR challenge does not burn the QR session, so a caller who only knows its UUID cannot disable the legitimate scanner. This limiter is shared with manual PR6 pairing.

| Endpoint | Caller/authentication | Request | Result |
|---|---|---|---|
| `POST /sync/admin/qr-sessions` | Web admin | empty | `201`, session fields and `qr_payload` |
| `GET /sync/admin/qr-sessions/{id}` | Web admin | — | id, status, device_name, device_id, created_at, expires_at |
| `POST /sync/qr-sessions/{id}/claim` | QR bearer capability | `challenge`, `device_name`, `device_credential` | `claim_ticket`, `confirmation_code`, status `CLAIMED` |
| `POST /sync/qr-sessions/{id}/ready` | `X-Claim-Ticket` | empty | status `AWAITING_CONFIRMATION` |
| `GET /sync/qr-sessions/{id}` | `X-Claim-Ticket` | — | current session status, device_id when paired |
| `POST /sync/admin/qr-sessions/{id}/confirm` | Web admin + human code | `confirmation_code` | status `PAIRED`, `device_id` |
| `POST /sync/admin/qr-sessions/{id}/reject` | Web admin | empty | `REJECTED` |
| `POST /sync/admin/qr-sessions/{id}/cancel` | Web admin | empty | `CANCELLED` |
| `GET /sync/admin/devices` | Web admin | — | paired/revoked device metadata and observed activity timestamps |
| `DELETE /sync/admin/devices/{device_id}` | Web admin | — | revoke credential; repeat is idempotent |
| `POST /sync/disconnect` | device bearer | empty | self-revoke the active device credential |

Concrete request/response shapes below reflect `backend/app/sync/qr.py` and Pydantic models. IDs are UUID strings and all timestamps include a timezone.

```json
{
  "data": {
    "id": "00000000-0000-4000-8000-000000000001",
    "status": "WAITING_FOR_DEVICE",
    "device_name": null,
    "device_id": null,
    "created_at": "2026-11-18T12:00:00Z",
    "expires_at": "2026-11-18T12:05:00Z",
    "qr_payload": {
      "version": 1,
      "base_url": "https://jlpt.example.test",
      "session_id": "00000000-0000-4000-8000-000000000001",
      "challenge": "<43-character-random-url-safe-value>",
      "expires_at": "2026-11-18T12:05:00Z"
    }
  }
}
```

The preceding shape is the successful `POST /sync/admin/qr-sessions` response (`201`).

Claim request constraints: `challenge` 24–100 characters; `device_name` 1–120 characters and non-blank after trimming; `device_credential` 48–200 URL-safe characters (`[A-Za-z0-9_-]`). Android creates the credential using a cryptographically secure RNG and stores it securely before claim. It must reuse exactly that credential when retrying this session.

Claim request JSON Schema:

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "additionalProperties": false,
  "required": ["challenge", "device_name", "device_credential"],
  "properties": {
    "challenge": { "type": "string", "minLength": 24, "maxLength": 100, "pattern": "^[A-Za-z0-9_-]+$" },
    "device_name": { "type": "string", "minLength": 1, "maxLength": 120 },
    "device_credential": { "type": "string", "minLength": 48, "maxLength": 200, "pattern": "^[A-Za-z0-9_-]+$" }
  }
}
```

```json
{
  "data": {
    "status": "CLAIMED",
    "claim_ticket": "<sha256-ticket>",
    "confirmation_code": "042731"
  }
}
```

The preceding shape is the successful `POST /sync/qr-sessions/{id}/claim` response (`200`).

Claim response JSON Schema:

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "additionalProperties": false,
  "required": ["data"],
  "properties": {
    "data": {
      "type": "object",
      "additionalProperties": false,
      "required": ["status", "claim_ticket", "confirmation_code"],
      "properties": {
        "status": { "const": "CLAIMED" },
        "claim_ticket": { "type": "string", "minLength": 64, "maxLength": 64, "pattern": "^[a-f0-9]{64}$" },
        "confirmation_code": { "type": "string", "pattern": "^[0-9]{6}$" }
      }
    }
  }
}
```

The confirmation request is `{"confirmation_code":"042731"}`. `GET /sync/admin/qr-sessions/{id}`, `/ready`, device status, confirm, reject and cancel responses expose `id`, `status`, `device_name`, `device_id`, `created_at`, and `expires_at`; the device status endpoint requires `X-Claim-Ticket`. Session status is one of `CREATED`, `WAITING_FOR_DEVICE`, `CLAIMED`, `AWAITING_CONFIRMATION`, `PAIRED`, `EXPIRED`, `REJECTED`, `CANCELLED`, or `FAILED`.

Claim request example (client generates a cryptographically random, URL-safe credential at least 48 characters and stores it securely **before** claim; claim retries reuse exactly the same credential):

```json
{
  "challenge": "<value-from-QR>",
  "device_name": "N3 Sensei phone",
  "device_credential": "<random-URL-safe-secret-at-least-48-characters>"
}
```

The server stores SHA-256 of challenge, ticket, confirmation code, and device credential, never their plaintext. A repeated identical claim returns the same ticket/code while pending. A different credential cannot take over the claimed session. Confirming a paired session is idempotent. Claiming it again returns `409`. Android must show the six-digit code to the human; Web asks the human to type the code and inspect the device name. The confirmation code is not sent to Web automatically from Android.

State machine:

```text
CREATED -> WAITING_FOR_DEVICE -> CLAIMED -> AWAITING_CONFIRMATION -> PAIRED
             |                   |               |
             +-------------------+---------------+--> EXPIRED / CANCELLED
                                 +---------------+--> REJECTED / FAILED
```

Only a session in `AWAITING_CONFIRMATION` can become `PAIRED`; a timed-out session cannot be completed. Creating a new QR session cancels all older unexpired, nonterminal QR sessions, so the Web operator has one current QR challenge at a time. Web administrator can revoke a paired device with `DELETE /sync/admin/devices/{device_id}`. Android can revoke itself with `POST /sync/disconnect` using bearer credential. Revocation makes subsequent device calls return `401`.

## Existing sync lifecycle after pairing

- The current Android client has manual pairing at `POST /sync/pair` with one-time `X-Pairing-Key`; it obtains a **different** server-generated bearer credential. Keep this path for old Android versions.
- The future QR client retains its own generated credential in Android Keystore-backed storage and sends `Authorization: Bearer <credential>` for `GET /sync/changes?cursor=N&limit=200` and `POST /sync/push`.
- `GET /sync/changes?cursor=0&limit=200` is the bootstrap; there is no separate QR-only bootstrap route. It returns `{ "data": { "data": [ ... ], "next_cursor": 0, "has_more": false } }`. Each change has `cursor`, `entity_type`, `entity_id`, `operation`, `version`, `changed_at`, `schema_version`, and `data` (`null` for a tombstone). Cursor is a server commit-ordered integer. Subsequent calls use the persisted checkpoint. Apply each page and checkpoint atomically in Room; never advance on failed validation. Page limit 1–500.
- Android PR6.1 recognizes only its existing Web mirrors: exam, passage, question, approved/current explanation, Web attempt/answer, knowledge, review item and review event. Unknown entity types must fail safely or be ignored only under an explicit compatible version policy. QR does **not** add Android local exam/progress/saved-word upload. Do not impersonate unsupported entity types.
- `POST /sync/push` accepts `{ "events": [...] }` with up to 500 append-only JLPT review events, each with UUID `request_id`, `item_type`, `item_id`, `rating`, timezone-aware timestamps, and intervals. The wrapped response contains `accepted[]` and `duplicates[]`, enabling safe retry with identical payload. Different payload using the same request ID is a conflict. Store pending events until acknowledgment; retain offline data.
- Verified exam answers stay server-authoritative. Existing Android `learning_progress`, `WordsReciteRecord`, Room database and SRS are never overwritten by this protocol.

## Mock test vectors and verification

`backend/tests/test_qr_pairing_v3.py` uses `https://jlpt.example.test`, claims with a random 48-byte URL-safe credential, retries the identical claim, checks wrong secret/ticket/code, calls ready then confirms, pulls with bearer credential and revokes. It also verifies expiry, cancellation/rotation of older QR sessions, rejection, loopback and malformed-origin rejection, exact QR payload fields, server-side secret hashing, the five-try confirmation limit and the shared source-address lockout. The example UUID/timestamp above illustrate shape, not a usable live QR. The test passes without Android or a public HTTPS endpoint.

To test with a **future** Android client: provision a trusted HTTPS hostname reachable by phone, set `SYNC_PUBLIC_HTTPS_BASE_URL`, migrate database to current head, open Settings → Đồng bộ Android, scan the QR, compare device name and six-digit code, confirm on Web, then pull/push and revoke. Verify the `last_pull_at` and `last_push_at` fields separately; paired alone is not synchronized.
